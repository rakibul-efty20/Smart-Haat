Backend Feature Specification\n5.1 API foundations and cross-cutting concerns\nRESTful endpoint conventions, correct HTTP methods/status codes, resource naming, pagination and consistent response/error shapes.\nDTOs for requests/responses; do not expose EF Core entities directly as public API contracts.\nDependency injection, configuration by environment, options validation and secure secret handling.\nGlobal exception handling using Problem Details or a consistent error contract; avoid leaking stack traces to clients.\nRequest validation using FluentValidation or a consistent built-in validation strategy.\nSwagger/OpenAPI documentation with bearer/cookie authentication guidance and example error responses.\nCORS restricted to known frontend origins; HTTPS in deployed environments.\nAPI versioning only if needed; document a policy before introducing multiple versions.\nRate limiting for login, password reset, coupon validation and order-creation endpoints.\nHealth checks for application readiness and critical dependencies; do not expose sensitive diagnostics publicly.\nStructured logging, correlation/request IDs, audit events for privileged changes, and safe handling of personal data.\nUse asynchronous I/O for database and network operations; avoid blocking calls in request paths.\n5.2 Authentication and identity\nCustomer registration, login, logout, email verification where feasible, forgot-password and reset-password flows.\nASP.NET Core Identity for password hashing and account management; never store plain-text passwords.\nShort-lived access token/session strategy and carefully designed refresh-token rotation/revocation if JWT is used.\nRoles and policy-based authorization for Customer, Salesman and Admin; finer-grained policies for sensitive actions.\nAccount activation/deactivation, failed-login protections and security-relevant audit events.\nAvoid storing long-lived refresh tokens in browser localStorage. Select a browser-appropriate session design, such as secure HttpOnly SameSite cookies or a backend-for-frontend approach, after considering CSRF and deployment architecture.\nUse secure password-reset tokens and never return secrets in API responses or logs.\n5.3 Product catalog and categories\nCategory hierarchy using ParentCategoryId, with safeguards against cycles and invalid parent references.\nProduct name, SKU, description, category, status, unit of measure, price and product media.\nProduct variants when needed (for example, size/weight/package) rather than forcing every variation into one product row.\nPublic product list with search, category filters, price range, sorting and pagination.\nProduct detail endpoint and active/inactive product visibility rules.\nAdmin create/update/archive operations, bulk price updates and image upload validation.\nImage storage abstraction, size/type limits, randomized file names and thumbnail/resize processing if practical.\nUse database indexes and SQL Server full-text search or indexed keyword search first. A separate search engine is optional, not mandatory.\n5.3.1 Admin Product Entry and Management\nProvide a protected admin product-management workflow so administrators can create, review, update, activate/deactivate and archive grocery products. The admin form must explicitly capture the product name, category, product image, price and relevant catalog details. Expiry information must be recorded against inventory batches, not only as one date on the product, because the same product can arrive in multiple batches with different expiry dates.\nProduct form fields: product name, SKU/code, category, optional brand, description, unit of measure, selling price, optional cost price, active status, and applicable tax/discount settings.\nCategory selection: choose an existing category from a searchable dropdown; allow category creation/editing only for users with the appropriate permission. Validate required fields and prevent duplicate SKUs.\nProduct image: upload one primary image initially, with optional gallery images later. Validate file type and size on the server, generate a safe random filename, store the image through an image-storage abstraction, and save only the storage key/URL in SQL Server. Do not trust the file extension or execute uploaded content.\nBatch and expiry entry: when receiving stock, create a batch with batch/lot number, received date, expiry/best-before date when applicable, received quantity, remaining quantity and optional supplier/cost reference. A product can have multiple batches.\nInventory validation: reject invalid quantities and dates, record stock receipt as a StockMovement, and retain an audit record of who created or changed product and batch information.\nEditing rules: changing a product's name, category, image or price must not rewrite historical order snapshots. Expiry dates and quantities are edited on the batch/stock-receiving workflow with appropriate permissions and audit logging.\nAdmin list screen: search by name/SKU, filter by category and active status, show thumbnail, price, available stock, nearest eligible expiry and low-stock/expiry warning indicators. Use pagination.\nSuggested API operations: GET /api/admin/products, GET /api/admin/products/{id}, POST /api/admin/products, PUT/PATCH /api/admin/products/{id}, POST /api/admin/products/{id}/image, and POST /api/admin/products/{id}/batches. Keep route naming consistent with the final API convention.\nAcceptance checks: an authorized admin can add a product with name/category/image; the product appears in the storefront when active; stock receipt creates a batch and stock movement; invalid image/SKU/price/date/quantity is rejected; unauthorized users cannot access admin operations.\n5.4 Cart and guest cart\nCustomer cart persisted by user identity and guest cart associated with a random, high-entropy guest token.\nAdd, update and remove cart items; validate product status, unit, quantity and stock availability.\nMerge guest cart into the signed-in user's cart after login using a documented conflict policy.\nTreat guest tokens as bearer secrets: do not use sequential IDs; avoid logging them; rotate or invalidate them when appropriate.\nRecalculate prices and discounts on the server. Cart totals are indicative and must be recalculated during checkout.\nDo not rely on the browser cart as the source of truth for price or stock.\n5.5 Pricing, discounts and coupons\nCentralized pricing service used by cart preview, checkout, POS and order preview so calculations remain consistent.\nMoney columns use an explicitly selected SQL decimal precision/scale (for example decimal(18,2) when the supported currency and business rules require two decimal places). Do not use floating-point types for money.\nDocument the price order: line subtotal → eligible member discount → coupon → delivery fee/tax if applicable → final payable total.\nDecide and test whether coupons stack with member discounts. A simple initial rule is to prohibit stacking or apply the better eligible discount, with explicit maximum-discount rules.\nCoupon code uniqueness, validity dates, minimum order, usage limit, per-customer limit, active status and product/category eligibility if required.\nApply coupon usage and order creation atomically enough to prevent simultaneous requests from exceeding limits.\nStore a price/discount/tax/shipping snapshot on the order so historical orders remain stable after product prices or rules change.\n5.6 Checkout and order lifecycle\nGuest checkout with name, phone, address and optional email; customer checkout using saved addresses.\nOrder preview endpoint returning a server-calculated price breakdown without creating an order.\nOrder creation with server-side recalculation of product prices, discounts, delivery fees and stock.\nOrder and order-item snapshots including SKU/name/unit price/quantity/discount and relevant product details.\nDistinct order status and payment status. Example order flow: Pending → Confirmed → Packed → Out for Delivery → Delivered; cancellation/refund paths are explicit rather than arbitrary status edits.\nCustomer order history and order detail with ownership checks.\nGuest order tracking using a high-entropy, unguessable tracking token or a combination of order reference and verified contact step. Do not expose private orders from a predictable order number alone.\nCancellation rules based on current status; record who made the change and why.\nInvoice/receipt generation can be added after core order correctness is proven.\n5.7 Inventory, stock movements and concurrency\nMaintain on-hand quantity and, if checkout needs it, reserved quantity; define available stock clearly as on-hand minus reserved stock.\nRecord every stock change in StockMovements with product/batch, signed quantity change, reason, reference entity, actor and timestamp.\nSupport restock, sale, cancellation return, manual adjustment, damage/waste, expiry disposal and stocktake correction.\nPerform order stock changes within database transactions and use SQL Server concurrency controls, such as rowversion, conditional updates or suitable locking.\nDefine how failed payment or cancelled orders release reserved stock. Avoid holding stock indefinitely.\nRestrict negative stock unless a deliberate business policy allows it; validate all changes on the server.\nKeep a clear audit trail for manual stock adjustments and require a reason.\n5.8 Food batches, expiry dates and alerts\nThis is a core feature for a grocery/food store, not merely a product-level date field. A product can have multiple batches with different quantities, receiving dates, suppliers and expiry dates. Track inventory at batch level so a sale or disposal can be attributed to the correct batch.\nProduct batch/lot records: product, batch number, received date, expiry/best-before date where applicable, received quantity, remaining quantity, cost if needed, supplier/reference and status.\nExpiry policy configurable by product/category: for example, alert at 30, 14, 7 and 1 day before expiry. These are example defaults, not universal food-safety rules.\nLow-stock threshold at product or inventory-location level, with ReorderLevel and current available quantity.\nAlert types: low stock, out of stock, approaching expiry, expired stock still on hand, and optionally high waste/near-expiry quantities.\nAdmin dashboard widget with severity, affected product/batch, quantity, expiry date and suggested action.\nScheduled background check that creates or updates alerts without creating duplicate alerts every run. Track alert status: Open, Acknowledged, Resolved, Dismissed.\nOptional email alerts through a configurable SMTP provider if available at no cost within the user's chosen service limits; the dashboard itself must work without email.\nExpiry handling: prevent expired batches from being sold where policy requires; ensure the checkout's stock allocation excludes expired or unavailable batches.\nUse FEFO (First Expired, First Out) allocation where appropriate: prefer eligible batches with the earliest expiry date. Keep the rule explicit and testable.\nRecord expired/damaged goods as waste or disposal stock movements; never silently delete the quantity.\nOptional later feature: supplier and purchase-receiving records to make batch/expiry data easier to populate.\nFood safety note: date labels and rules differ by product and jurisdiction. The system should support configurable policies and human review rather than pretending that one global expiry rule is legally correct.\n5.9 Staff POS and in-store sales\nStaff creates a sale by searching/selecting products, entering quantities and confirming price totals.\nSupport cash/Cash on Delivery and a generic recorded payment method first; online payment integration can be added separately.\nRecord CreatedBy/SalesmanId, order channel (Online/POS), payment status and relevant receipt reference.\nRestrict discounts and void/refund actions by policy; log overrides and reasons.\nUse the same pricing, stock and order services as online checkout so the two channels cannot calculate different totals.\nSalesman reporting is scoped to permitted orders; administrators can view global reports.\n5.10 Users, audit, reports and notifications\nAdmin can list users, activate/deactivate accounts and create staff accounts through protected workflows.\nAudit logs record sensitive changes such as price updates, stock adjustments, coupon changes, role changes and order-status overrides. Store meaningful before/after data while avoiding secrets.\nReports: daily/weekly/monthly sales, order count, average order value, top-selling products, category sales, low stock, near-expiry stock, expired/wasted stock and sales by channel/staff.\nDefine report semantics: gross sales, discounts, refunds, cancelled orders and net sales must be handled consistently.\nUse database aggregation and pagination; do not load all historical orders into memory to calculate a dashboard.\nOrder confirmation and status notification through email/SMS can be optional adapters. The core system must not require a paid messaging API.\nGenerate CSV exports first as a free, useful reporting feature; PDF invoices are a later enhancement.\n6. Security and Reliability Checklist\nEnforce authorization at every protected API endpoint; test customer-to-customer data isolation.\nValidate every request on the server; normalize and constrain inputs.\nUse HTTPS in production and secure cookie/token settings appropriate to the chosen session design.\nKeep secrets in environment configuration or a secret store, never in source control or frontend bundles.\nProtect login, password reset, coupon validation, guest tracking and order creation against abuse.\nUse safe upload rules: allowlisted file types, size limits, randomized storage names and no execution of uploaded content.\nPrevent SQL injection by using EF Core parameterization and safe query construction.\nUse transactions and concurrency controls for inventory and coupon usage.\nDesign payment webhooks for signature validation, idempotency and safe retries.\nLog security-relevant events without logging passwords, access tokens, refresh tokens, full payment data or unnecessary personal details.\nUse database backups and test restoration; backups are not useful until recovery has been tested.\nTrack dependency updates and scan packages/secrets in CI.\nUse a consistent error contract; production errors must not expose stack traces, SQL details or secrets.\nDefine data retention, account deactivation and audit log access rules.\n11.
