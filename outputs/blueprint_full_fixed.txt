## 3. Confirmed architecture and quality requirements
Admin bootstrap: provide a secure development-only way to create the first Admin account. Never ship a default production password or enable development bootstrap in production.
Initial tax scope: no tax calculation in the first version. Keep this explicit in price/order calculations and documentation rather than silently adding tax.
Images: use local file storage for development behind an image-storage abstraction. Validate uploaded content and size, generate safe random file names, and store a storage key/URL in the database. A different provider can be introduced later.
Delivery: support configurable delivery zones/areas and delivery fees stored in the database; do not require a paid maps API for the initial implementation.
Product variants: keep the architecture extensible for variants, but implement them only when a real product requirement needs them; they are not mandatory for the first catalog phase.
Order visibility: Salesman/staff users can access only their own or assigned orders. Admin users can access all orders. Enforce these restrictions in backend queries and authorization rules.
Inventory and expiry: track stock in inventory batches, not as a single expiry date on the product. Use appropriate batch allocation (including FEFO where suitable), stock movements, concurrency protection, and configurable low-stock/near-expiry thresholds.
Stock reservation: reserve stock when an order is created. Reservations must have an expiry/release policy so abandoned, expired, or cancelled orders do not hold stock indefinitely.
Discount policy: do not stack eligible discounts. Calculate the eligible alternatives and apply only the better discount, with the rule covered by automated tests.
Initial payment methods: Cash on Delivery (COD) for online orders and cash for staff POS orders. Do not handle or store raw card details. Additional payment providers can be added behind an abstraction later.
Currency: Bangladeshi taka (BDT). Use decimal monetary values and explicit database precision; do not add tax calculation in the initial version.

## REVISION 1 — CONFIRMED PROJECT DECISIONS
## 1. Executive Summary
Build Smart-Haat, a portfolio-quality grocery e-commerce management system for a small grocery/food retailer. It supports a public storefront, customer accounts, guest checkout, shopping carts, coupons, inventory, food expiry tracking, staff-assisted point-of-sale (POS) orders, admin management, and sales reporting.
The project should demonstrate the complete lifecycle of a modern web application: requirements, modular backend design, database modeling, REST API design, frontend integration, authentication and authorization, validation, testing, logging, deployment, and documentation. The target is not to imitate a huge enterprise platform with dozens of services; it is to deliver a reliable modular monolith with clear boundaries and demonstrable engineering decisions.
## Primary goals
Use ASP.NET Core Web API on .NET 10, Angular 22 in zoneless mode, and Microsoft SQL Server.
Apply the relevant skills from Trevoir Williams' ASP.NET Core Web API course: REST, EF Core, DI, DTOs, service/repository boundaries, Identity/JWT, Swagger/OpenAPI, logging, middleware, validation and deployment.
Support both online customer orders and staff-created in-store/POS orders.
Track stock movements and food batches/expiry dates, with configurable low-stock and near-expiry alerts.
Use free or open-source tools and free-tier/local development options; avoid mandatory paid APIs.
Build in small, complete, testable phases suitable for a student schedule and job interviews.

## 5. Backend Feature Specification
## 5.1 API foundations and cross-cutting concerns
RESTful endpoint conventions, correct HTTP methods/status codes, resource naming, pagination and consistent response/error shapes.
DTOs for requests/responses; do not expose EF Core entities directly as public API contracts.
Dependency injection, configuration by environment, options validation and secure secret handling.
Global exception handling using Problem Details or a consistent error contract; avoid leaking stack traces to clients.
Request validation using FluentValidation or a consistent built-in validation strategy.
Swagger/OpenAPI documentation with bearer/cookie authentication guidance and example error responses.
CORS restricted to known frontend origins; HTTPS in deployed environments.
API versioning only if needed; document a policy before introducing multiple versions.
Rate limiting for login, password reset, coupon validation and order-creation endpoints.
Health checks for application readiness and critical dependencies; do not expose sensitive diagnostics publicly.
Structured logging, correlation/request IDs, audit events for privileged changes, and safe handling of personal data.
Use asynchronous I/O for database and network operations; avoid blocking calls in request paths.
## 5.2 Authentication and identity
Customer registration, login, logout, email verification where feasible, forgot-password and reset-password flows.
ASP.NET Core Identity for password hashing and account management; never store plain-text passwords.
Short-lived access token/session strategy and carefully designed refresh-token rotation/revocation if JWT is used.
Roles and policy-based authorization for Customer, Salesman and Admin; finer-grained policies for sensitive actions.
Account activation/deactivation, failed-login protections and security-relevant audit events.
Avoid storing long-lived refresh tokens in browser localStorage. Select a browser-appropriate session design, such as secure HttpOnly SameSite cookies or a backend-for-frontend approach, after considering CSRF and deployment architecture.
Use secure password-reset tokens and never return secrets in API responses or logs.
## 5.3 Product catalog and categories
Category hierarchy using ParentCategoryId, with safeguards against cycles and invalid parent references.
Product name, SKU, description, category, status, unit of measure, price and product media.
Product variants when needed (for example, size/weight/package) rather than forcing every variation into one product row.
Public product list with search, category filters, price range, sorting and pagination.
Product detail endpoint and active/inactive product visibility rules.
Admin create/update/archive operations, bulk price updates and image upload validation.
Image storage abstraction, size/type limits, randomized file names and thumbnail/resize processing if practical.
Use database indexes and SQL Server full-text search or indexed keyword search first. A separate search engine is optional, not mandatory.
## 5.3.1 Admin Product Entry and Management
Provide a protected admin product-management workflow so administrators can create, review, update, activate/deactivate and archive grocery products. The admin form must explicitly capture the product name, category, product image, price and relevant catalog details. Expiry information must be recorded against inventory batches, not only as one date on the product, because the same product can arrive in multiple batches with different expiry dates.
Product form fields: product name, SKU/code, category, optional brand, description, unit of measure, selling price, optional cost price, active status, and applicable tax/discount settings.
Category selection: choose an existing category from a searchable dropdown; allow category creation/editing only for users with the appropriate permission. Validate required fields and prevent duplicate SKUs.
Product image: upload one primary image initially, with optional gallery images later. Validate file type and size on the server, generate a safe random filename, store the image through an image-storage abstraction, and save only the storage key/URL in SQL Server. Do not trust the file extension or execute uploaded content.
Batch and expiry entry: when receiving stock, create a batch with batch/lot number, received date, expiry/best-before date when applicable, received quantity, remaining quantity and optional supplier/cost reference. A product can have multiple batches.
Inventory validation: reject invalid quantities and dates, record stock receipt as a StockMovement, and retain an audit record of who created or changed product and batch information.
Editing rules: changing a product's name, category, image or price must not rewrite historical order snapshots. Expiry dates and quantities are edited on the batch/stock-receiving workflow with appropriate permissions and audit logging.
Admin list screen: search by name/SKU, filter by category and active status, show thumbnail, price, available stock, nearest eligible expiry and low-stock/expiry warning indicators. Use pagination.
Suggested API operations: GET /api/admin/products, GET /api/admin/products/{id}, POST /api/admin/products, PUT/PATCH /api/admin/products/{id}, POST /api/admin/products/{id}/image, and POST /api/admin/products/{id}/batches. Keep route naming consistent with the final API convention.
Acceptance checks: an authorized admin can add a product with name/category/image; the product appears in the storefront when active; stock receipt creates a batch and stock movement; invalid image/SKU/price/date/quantity is rejected; unauthorized users cannot access admin operations.
## 5.4 Cart and guest cart
Customer cart persisted by user identity and guest cart associated with a random, high-entropy guest token.
Add, update and remove cart items; validate product status, unit, quantity and stock availability.
Merge guest cart into the signed-in user's cart after login using a documented conflict policy.
Treat guest tokens as bearer secrets: do not use sequential IDs; avoid logging them; rotate or invalidate them when appropriate.
Recalculate prices and discounts on the server. Cart totals are indicative and must be recalculated during checkout.
Do not rely on the browser cart as the source of truth for price or stock.
## 5.5 Pricing, discounts and coupons
Centralized pricing service used by cart preview, checkout, POS and order preview so calculations remain consistent.
Money columns use an explicitly selected SQL decimal precision/scale (for example decimal(18,2) when the supported currency and business rules require two decimal places). Do not use floating-point types for money.
Document the price order: line subtotal → eligible member discount → coupon → delivery fee/tax if applicable → final payable total.
Decide and test whether coupons stack with member discounts. A simple initial rule is to prohibit stacking or apply the better eligible discount, with explicit maximum-discount rules.
Coupon code uniqueness, validity dates, minimum order, usage limit, per-customer limit, active status and product/category eligibility if required.
Apply coupon usage and order creation atomically enough to prevent simultaneous requests from exceeding limits.
Store a price/discount/tax/shipping snapshot on the order so historical orders remain stable after product prices or rules change.
## 5.6 Checkout and order lifecycle
Guest checkout with name, phone, address and optional email; customer checkout using saved addresses.
Order preview endpoint returning a server-calculated price breakdown without creating an order.
Order creation with server-side recalculation of product prices, discounts, delivery fees and stock.
Order and order-item snapshots including SKU/name/unit price/quantity/discount and relevant product details.
Distinct order status and payment status. Example order flow: Pending → Confirmed → Packed → Out for Delivery → Delivered; cancellation/refund paths are explicit rather than arbitrary status edits.
Customer order history and order detail with ownership checks.
Guest order tracking using a high-entropy, unguessable tracking token or a combination of order reference and verified contact step. Do not expose private orders from a predictable order number alone.
Cancellation rules based on current status; record who made the change and why.
Invoice/receipt generation can be added after core order correctness is proven.
## 5.7 Inventory, stock movements and concurrency
Maintain on-hand quantity and, if checkout needs it, reserved quantity; define available stock clearly as on-hand minus reserved stock.
Record every stock change in StockMovements with product/batch, signed quantity change, reason, reference entity, actor and timestamp.
Support restock, sale, cancellation return, manual adjustment, damage/waste, expiry disposal and stocktake correction.
Perform order stock changes within database transactions and use SQL Server concurrency controls, such as rowversion, conditional updates or suitable locking.
Define how failed payment or cancelled orders release reserved stock. Avoid holding stock indefinitely.
Restrict negative stock unless a deliberate business policy allows it; validate all changes on the server.
Keep a clear audit trail for manual stock adjustments and require a reason.
## 5.8 Food batches, expiry dates and alerts
This is a core feature for a grocery/food store, not merely a product-level date field. A product can have multiple batches with different quantities, receiving dates, suppliers and expiry dates. Track inventory at batch level so a sale or disposal can be attributed to the correct batch.
Product batch/lot records: product, batch number, received date, expiry/best-before date where applicable, received quantity, remaining quantity, cost if needed, supplier/reference and status.
Expiry policy configurable by product/category: for example, alert at 30, 14, 7 and 1 day before expiry. These are example defaults, not universal food-safety rules.
Low-stock threshold at product or inventory-location level, with ReorderLevel and current available quantity.
Alert types: low stock, out of stock, approaching expiry, expired stock still on hand, and optionally high waste/near-expiry quantities.
Admin dashboard widget with severity, affected product/batch, quantity, expiry date and suggested action.
Scheduled background check that creates or updates alerts without creating duplicate alerts every run. Track alert status: Open, Acknowledged, Resolved, Dismissed.
Optional email alerts through a configurable SMTP provider if available at no cost within the user's chosen service limits; the dashboard itself must work without email.
Expiry handling: prevent expired batches from being sold where policy requires; ensure the checkout's stock allocation excludes expired or unavailable batches.
Use FEFO (First Expired, First Out) allocation where appropriate: prefer eligible batches with the earliest expiry date. Keep the rule explicit and testable.
Record expired/damaged goods as waste or disposal stock movements; never silently delete the quantity.
Optional later feature: supplier and purchase-receiving records to make batch/expiry data easier to populate.
Food safety note: date labels and rules differ by product and jurisdiction. The system should support configurable policies and human review rather than pretending that one global expiry rule is legally correct.
## 5.9 Staff POS and in-store sales
Staff creates a sale by searching/selecting products, entering quantities and confirming price totals.
Support cash/Cash on Delivery and a generic recorded payment method first; online payment integration can be added separately.
Record CreatedBy/SalesmanId, order channel (Online/POS), payment status and relevant receipt reference.
Restrict discounts and void/refund actions by policy; log overrides and reasons.
Use the same pricing, stock and order services as online checkout so the two channels cannot calculate different totals.
Salesman reporting is scoped to permitted orders; administrators can view global reports.
## 5.10 Users, audit, reports and notifications
Admin can list users, activate/deactivate accounts and create staff accounts through protected workflows.
Audit logs record sensitive changes such as price updates, stock adjustments, coupon changes, role changes and order-status overrides. Store meaningful before/after data while avoiding secrets.
Reports: daily/weekly/monthly sales, order count, average order value, top-selling products, category sales, low stock, near-expiry stock, expired/wasted stock and sales by channel/staff.
Define report semantics: gross sales, discounts, refunds, cancelled orders and net sales must be handled consistently.
Use database aggregation and pagination; do not load all historical orders into memory to calculate a dashboard.
Order confirmation and status notification through email/SMS can be optional adapters. The core system must not require a paid messaging API.
Generate CSV exports first as a free, useful reporting feature; PDF invoices are a later enhancement.

## Database integrity rules
Use decimal columns for money; choose currency and scale deliberately.
Use UTC timestamps in storage where appropriate and convert to local time in the UI/reporting layer.
Use rowversion or another explicit concurrency strategy for inventory-sensitive records.
Use foreign keys, check constraints, unique indexes and non-null rules to protect core invariants.
Prefer inactive/archive states over deleting products or users that are referenced by historical orders.
Keep order snapshots even when the current product name, price or address changes.
Create indexes for SKU, active product/category browsing, order number, user/order history, status/date reports, batch expiry and alert status.
Design stock movement and order changes so they can be audited and reconciled.

## API conventions
Use explicit request/response DTOs and consistent validation errors.
Paginate every potentially large list; set maximum page size.
Use appropriate status codes and distinguish validation, authentication, authorization, not-found and conflict responses.
Consider idempotency keys for order/payment operations where duplicate submissions would be harmful.
Use optimistic concurrency/ETag or rowversion-based conflict responses where appropriate.
Never accept price, discount or stock totals from the browser as authoritative.

## Frontend engineering guidance
Use standalone components and lazy-loaded feature routes.
Use Angular signals and services for local/shared state at first; introduce NgRx or another store only when state complexity justifies it.
For zoneless Angular, follow Angular 22's supported zoneless setup and change-detection guidance. Prefer signals, async-aware templates and documented notification mechanisms over assumptions based on Zone.js.
Use reactive forms or the current recommended Angular form approach consistently, with clear validation and accessible error messages.
Use an HTTP interceptor for common headers and error handling. Avoid assuming that putting JWTs in localStorage is the safest browser session strategy.
Route guards are a navigation aid, not backend security.
Use Angular Material or PrimeNG if it helps build consistent admin tables and forms quickly; both are optional. Check each library's compatibility with the chosen Angular major version.
Use a chart library only after report APIs are correct; charts must reflect clearly defined sales metrics.
Support responsive layouts, keyboard navigation, visible focus, labels, loading states, empty states and useful error messages.

## External service policy
No paid API is required to build or demonstrate the core application.
Keep email, payment, image storage and messaging behind interfaces so they can be disabled or replaced.
For the first demo, use Cash on Delivery and/or a payment sandbox. Clearly label simulated payments and never claim that a mock payment is a real transaction.
Avoid dependence on Google Maps or another paid map API for delivery zones. Start with configurable city/area/zone data and delivery-fee rules in SQL Server.
Do not integrate SMS until the project genuinely needs it; show order updates in the app and use local email capture for development.
Verify current free-tier terms at the time of deployment; do not hard-code an assumption that a third-party service will remain free.
## 10. Security and Reliability Checklist
Enforce authorization at every protected API endpoint; test customer-to-customer data isolation.
Validate every request on the server; normalize and constrain inputs.
Use HTTPS in production and secure cookie/token settings appropriate to the chosen session design.
Keep secrets in environment configuration or a secret store, never in source control or frontend bundles.
Protect login, password reset, coupon validation, guest tracking and order creation against abuse.
Use safe upload rules: allowlisted file types, size limits, randomized storage names and no execution of uploaded content.
Prevent SQL injection by using EF Core parameterization and safe query construction.
Use transactions and concurrency controls for inventory and coupon usage.
Design payment webhooks for signature validation, idempotency and safe retries.
Log security-relevant events without logging passwords, access tokens, refresh tokens, full payment data or unnecessary personal details.
Use database backups and test restoration; backups are not useful until recovery has been tested.
Track dependency updates and scan packages/secrets in CI.
Use a consistent error contract; production errors must not expose stack traces, SQL details or secrets.
Define data retention, account deactivation and audit log access rules.

## 15. Scope Boundaries — What to Avoid Initially
Do not start with microservices, Kubernetes, event sourcing or a distributed cache cluster. They increase complexity without proving the core business works.
Do not add a separate search engine, Redis, message broker and multiple background job systems simultaneously.
Do not implement real card storage or handle raw card details; use a reputable payment provider when payment integration is introduced.
Do not treat a frontend guard, hidden button or secret URL as authorization.
Do not trust client-supplied prices, discount amounts, order totals or stock counts.
Do not use a single ExpiryDate on Products when multiple food batches can expire at different times.
Do not let a recurring alert job create a new duplicate alert every time it runs.
Do not claim the project is fully production-ready merely because it runs on a free host; document operational and service limits.
## 16. Decisions to Lock Before Implementation
[TABLE]
Decision | Recommended starting choice
Salesman order visibility | Own/assigned sales only by default; Admin sees all. Document whether POS sales can be transferred or reassigned.
Discount stacking | Initially prohibit coupon + member discount stacking, or apply the better eligible discount. Make the rule explicit in tests.
Stock allocation | Track batch quantities and use FEFO for eligible food batches where appropriate; define reservation timing for online checkout.
Guest tracking | Use an unguessable tracking token or verified contact flow; never rely on sequential order numbers alone.
Payment | Start with COD and clearly labeled sandbox/mock flows; integrate live provider only after merchant requirements and fees are confirmed.
Delivery charge | Start with configurable city/area/zone rules in SQL Server, not a paid maps API.
Notifications | Use in-app status and local email capture first; keep real email/SMS optional.
Deployment | Make a local reproducible demo first; choose hosting only after checking current free-tier limits and SQL Server compatibility.
Currency and tax | Define supported currency, rounding, tax and delivery-fee rules before finalizing decimal precision and price calculations.
Expiry policy | Make thresholds configurable by product/category; distinguish best-before and use-by/expiry semantics where the business needs them.
